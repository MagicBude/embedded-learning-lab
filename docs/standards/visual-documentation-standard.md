# 可视化文档规范

## 目标

可视化用于降低理解复杂关系、流程、状态、时序和空间结构的成本。图表必须承担信息表达职责，不能只是装饰。

## 表达方式选择

| 内容 | 首选表达 |
| --- | --- |
| 仓库和目录结构 | ASCII Tree |
| 页面信息层级 | ASCII Wireframe |
| 框图、流程与依赖 | diagrams.net 源文件，导出 SVG |
| 多层关系或需要稳定版式的架构图 | diagrams.net 源文件，导出 SVG |
| 生命周期和状态转换 | diagrams.net 源文件，导出 SVG |
| 模块交互和调用顺序 | diagrams.net 源文件，导出 SVG |
| 数据实体关系 | diagrams.net 源文件，导出 SVG |
| 协议时序、波形和总线拓扑 | diagrams.net 源文件，导出 SVG |
| 内存布局、帧格式和寄存器结构 | diagrams.net 源文件并导出 SVG，或语义化 HTML |
| 参数变化与机制探索 | 交互组件 |
| 数值比较和趋势 | 图表，并明确单位和数据来源 |

## 正式图源与导出规则

- 正式框图统一在 `docs/assets/diagrams/` 中保存同名 `.drawio` 源文件和 `.svg` 导出文件；
- Markdown 只引用 `.svg`，`.drawio` 用于后续编辑；
- Mermaid 仅用于讨论中的临时草图，不作为正式文档图源；
- 节点使用项目中的稳定术语；
- 流向保持一致，优先从左到右或从上到下；
- 一张图只解释一个核心问题；
- 当节点和交叉连线过多时，拆成上下文图、容器图和局部流程图；
- 图后必须有必要的正文解释，不能要求读者仅凭图猜测约束；
- 修改 `.drawio` 后必须重新导出并检查 `.svg`，两者表达必须一致。

## ASCII 图规则

- ASCII Tree 用于表达文件层级，不用于表达复杂流程；
- ASCII Wireframe 只表达页面区域、顺序和层级，不提前决定视觉风格；
- 保持普通等宽字体下可读；
- 当移动端和桌面端结构不同，应分别绘制。

## 技术图规则

- 波形、拓扑、状态和电气图优先使用可缩放的 SVG；
- 技术图中的单位、方向、信号名和条件必须明确；
- 不能只使用颜色表达状态或信号；
- Light / Dark 模式下都应保持可读；
- 动画必须支持 `prefers-reduced-motion`；
- 如果图中包含技术结论，应在正文中标出来源或验证条件。

## 正式框图规则

- 对外展示或承担核心说明职责的图，统一使用 diagrams.net 维护并导出 SVG；
- 使用统一的圆角节点、字号、颜色和箭头样式；
- 优先使用直线或正交连线，禁止无必要的交叉；
- 连线不得穿过任何节点；
- 箭头必须停在目标节点边框上，并对准所连接边的中点，不得落在边角或伸入节点内部；
- 同一节点有多条出线时，先在节点外部建立分支通道，再分别连接目标；
- 主流程与反馈、异常、引用关系使用不同线型；
- 跨模块的非层级关系优先放在正文或关系表中，不强行全部画进一张图；
- SVG 必须包含 `<title>` 和 `<desc>`，并兼容浅色与深色模式；
- 修改后必须查看实际渲染结果，不能只检查 SVG 源码。

## 交互可视化规则

只有满足以下条件之一才使用交互：

- 改变参数能帮助理解因果关系；
- 状态或时序需要逐步观察；
- 静态图无法清晰展示所有重要情况；
- 用户需要通过实验形成直觉。

交互内容应：

- 有明确学习目标；
- 提供合理默认状态；
- 支持键盘和触摸；
- 在交互不可用时仍提供文字说明；
- 将领域模型、计算逻辑和视觉渲染尽量分离；
- 对关键计算和状态转换提供测试。

## 禁止事项

- 不使用无教学意义的背景动画；
- 不为每段文字重复绘图；
- 不使用 AI 生成图片代替需要精确表达的技术图；
- 不把截图作为可维护架构图的唯一来源；
- 不制作一张试图覆盖整个产品所有细节的巨型图；
- 不让视觉效果覆盖技术准确性。

## 文档最低图表要求

以下文档原则上应包含对应图示：

- 项目章程：项目价值循环；
- 内容模型：来源关系和内容生命周期；
- 信息架构：网站地图和首页 Wireframe；
- 技术架构：系统上下文和内容构建流水线；
- 路线图：阶段演进；
- 复杂功能设计：用户流程、状态机或时序图。
